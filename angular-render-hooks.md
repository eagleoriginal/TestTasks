# Render-хуки и жизненный цикл: что когда готово

Шпаргалка по Angular **21.2.16**. Всё, что помечено ссылкой на файл, сверено с
`node_modules/@angular/core/` — именно эта часть API переименовывалась и переезжала между
версиями, так что советы из интернета трёхлетней давности здесь врут.

Парный документ: [angular-change-detection-zoneless.md](angular-change-detection-zoneless.md).

---

## 1. Первое, что экономит полчаса: `afterRender` больше нет

В версии 21 функция называется **`afterEveryRender`**. Идентификатора `afterRender` в публичном
API нет вообще — ноль вхождений в `types/core.d.ts`, в списке экспортов
(`types/core.d.ts:9453`) значатся только:

```
afterEveryRender, afterNextRender, afterRenderEffect
```

Так что три функции, а не «afterRender и почему-то ещё afterNextRender»:

| Функция | Сколько раз выполнится | Реагирует на сигналы |
|---|---|---|
| `afterNextRender` | **один раз**, после ближайшей отрисовки | нет |
| `afterEveryRender` | после **каждой** отрисовки | нет |
| `afterRenderEffect` | как эффект: при старте и при изменении прочитанных сигналов | да |

## 2. Фаз четыре, а не три

`types/core.d.ts:2300-2327`. Все три функции принимают либо простой коллбэк, либо объект с
фазами:

```ts
afterNextRender({
  earlyRead:      () => …,   // 1. читать DOM (когда без этого никак)
  write:          (e) => …,  // 2. писать в DOM
  mixedReadWrite: (w) => …,  // 3. читать и писать вперемешку
  read:           (m) => …,  // 4. читать DOM
}, { injector });
```

Порядок выполнения жёсткий: `earlyRead` → `write` → `mixedReadWrite` → `read`
(в рантайме это `AFTER_RENDER_PHASES = [0, 1, 2, 3]`,
`fesm2022/_debug_node-chunk.mjs:4398`).

**Важно:** фаза — внешний цикл, а тип функции не влияет на порядок вообще. `write` из
`afterEveryRender` выполнится раньше, чем `read` из `afterRenderEffect`, и наоборот. Подробнее —
§6 парного документа.

### Модель браузера, без которой фазы выглядят произволом

Одна аналогия, и дальше всё выводится: **layout — это ленивый кэш, как отложенный flush в ORM.**

Браузер **не** пересчитывает геометрию после каждого изменения DOM. Он помечает её грязной и
откладывает — до отрисовки кадра или до момента, когда кто-то спросит конкретное число.

- **Испачкать** = записать что-либо, влияющее на геометрию: `style`, класс, добавление или
  удаление узла, `textContent`. Это дёшево, пересчёта не происходит.
- **Спросить** = прочитать вычисляемое свойство: `getBoundingClientRect()`, `offsetHeight`,
  `offsetTop`, `clientWidth`, `scrollTop`, `scrollHeight`, `getComputedStyle()`. Вот это
  **форсирует пересчёт немедленно**, если кэш грязный. Иначе браузер не смог бы вернуть
  правильное число.

Отсюда сразу видно, что дорого:

```js
for (const el of elements) {
  el.style.width = '100px';           // испачкали
  console.log(el.offsetHeight);       // ← ПЕРЕСЧЁТ всей страницы
}                                     // N элементов = N пересчётов
```

Это и называется **layout thrashing**. Перестановка в два цикла — сначала все записи, потом все
чтения — даёт **один** пересчёт вместо N. Фазы Angular именно это и делают, только между
разными компонентами, которые друг о друге не знают и сами договориться не могут.

### Что означает каждая фаза

| Фаза | Что уже произошло | Что здесь делать | Чего здесь нельзя |
|---|---|---|---|
| `earlyRead` | Angular обновил DOM; layout грязный после этого | мерить **исходное** состояние | писать — испортишь замеры соседям |
| `write` | все замеры собраны | писать сколько угодно | **читать геометрию** — форсируешь пересчёт посреди записей |
| `mixedReadWrite` | часть записей уже сделана | и читать, и писать | по возможности — находиться здесь |
| `read` | все записи сделаны | мерить **результат** | писать — снова испачкаешь кэш |

Итоговая цена: примерно два пересчёта на весь проход — один на группу `earlyRead`, один на
группу `read` — вместо одного на каждый компонент.

### Ответы на «а этот-то зачем»

**Почему в `write` нельзя читать.** Писать можно что угодно, запрет ровно один: не спрашивать у
браузера числа. Один такой вопрос посреди фазы записи форсирует пересчёт и обнуляет всю выгоду
от группировки — причём не тебе, а всем остальным.

**Зачем `mixedReadWrite`.** Это не «удобный универсальный», а аварийный выход для кода, который
физически нельзя разделить, потому что он не твой: сторонняя библиотека, у которой внутри одного
вызова `.render()` и замеры, и записи. Разбить чужой вызов на две фазы невозможно. Своей код
сюда попадать не должен — и документация Angular помечает это как критичное для
производительности. В этом репозитории в `mixedReadWrite` сидит `extra-panel`, и там это
оправдано лишь наполовину: замеры можно было бы вынести в `earlyRead`.

**Зачем финальный `read` — «фотография итога».** Формулировка точная, и вот когда она нужна:

- **измерить последствия собственной записи.** Поставил ширину — узнать, во сколько строк
  завернулся текст и какой стала высота. В `earlyRead` этого числа ещё не существует;
- **положить замер в состояние.** Именно это делает `extra-panel`: меряет, а в `read` пишет
  сигнал `shouldShowExtraBtn`, по которому решается, показывать ли кнопку «развернуть»;
- **проскроллить к тому, что только что появилось.** Позиция известна только после записей;
- **отдать финальную геометрию наружу** — в аналитику, в родителя, в не-Angular виджет.

Короткая формула: **`earlyRead` отвечает на вопрос «как есть сейчас», `read` — «что
получилось».** Если тебе не нужно ни то, ни другое — не бери ни одну из них, бери `write`.

### Прочее

Angular не может проверить, что ты действительно только читаешь в `read` — это соглашение,
которое соблюдает разработчик. Документация прямо просит предпочитать `read` и `write`, а
`earlyRead`/`mixedReadWrite` брать только когда иначе никак.

Значение, возвращённое из фазы, приезжает параметром в следующую — так передают между ними
измеренную геометрию, не складывая её в поля компонента.

Простой коллбэк без объекта = фаза `mixedReadWrite` (`types/core.d.ts:2399`). То есть **самый
короткий способ записи — заодно и самый вредный для производительности.** Фазу лучше указывать
всегда.

## 3. Ни один из них не выполняется на сервере

Прямая цитата из документации API (`types/core.d.ts:2642`):

> `afterRenderEffect`s run on browser platforms only, they will not run on the server.

То же сказано про `afterEveryRender` и `afterNextRender`.

**Это главный практический факт для SSG.** Если логика зависит от URL, `localStorage`,
размеров элемента или чего угодно, чего нет при запекании, — ей место в render-хуке, и тогда
она гарантированно не попадёт в запечённый HTML.

Обратная сторона: всё, что в `ngOnInit`, **выполняется и при запекании тоже**, и результат
вмерзает в артефакт. Именно так у нас получились 243-байтные заглушки с
`<meta http-equiv="refresh">` вместо страниц — см. §7 в
[encoding-contexts.md](encoding-contexts.md) и раздел 6 ниже.

## 4. Когда именно они выполняются

Не отдельным механизмом, а **внутри того же прохода change detection**, последним шагом —
`ApplicationRef.synchronizeOnce()`, `fesm2022/_debug_node-chunk.mjs:12462-12495`:

```
1. rootEffectScheduler.flush()      корневые effect()
2. detectChangesInternal(...)       обход видов, обновление DOM
3. (если снова появились «видовые» биты — выход, оборот заново)
4. afterRenderManager.execute()     ← render-хуки
```

Главное следствие: **хук видит DOM уже обновлённым.** Для этого он и нужен — `ngAfterViewInit`
срабатывает до того, как отрисовка завершилась, и мерить геометрию там рано.

### Ставит ли `afterNextRender` отрисовку в очередь

В разных источниках написано и «ставит», и «не ставит». Оба утверждения верны, просто **про
разные моменты**, и путаница ровно в том, что их не разделяют.

| Момент | Будит ли отрисовку |
|---|---|
| **Регистрация** — сам вызов `afterNextRender(...)` | **да**, всегда |
| **Тело** — выполнение твоего коллбэка | **нет**, само по себе ничего не грязнит |

**Регистрация будит.** Иначе и быть не может: ты просишь выполнить код после отрисовки, значит
отрисовка должна случиться, даже если больше в приложении ничего не менялось. Angular ставит
проход в очередь в момент регистрации.

**Тело не грязнит.** Хук ничего не помечает для проверки. Очередь появляется только от того,
что ты написал внутри: записал сигнал, позвал `markForCheck()`, изменил вход дочернего
компонента.

### Практическое следствие, которое реально стреляет

Из конструктора это незаметно — компонент и так создаётся внутри прохода, отрисовка всё равно
будет.

А вот **вызов позже — из обработчика события, из подписки, из таймера — сам разбудит
отрисовку.** `afterNextRender` не является пассивным «дождаться следующего кадра, если он
вообще случится». Он этот кадр вызывает.

Отсюда: не вешать `afterNextRender` внутри чего-то, что срабатывает часто (скролл, ввод,
`mousemove`) в надежде «замерю, когда браузер и так перерисует». Каждый такой вызов — это ещё
один запланированный проход change detection.

### Когда хук всё-таки крутит цикл заново

Два законных случая:

- **внутри хука ты что-то пометил грязным** — тогда источником будет то, что ты сделал
  (`MarkForCheck`, запись сигнала и т.д.), и цикл провернётся ещё раз;
- **внутри хука ты зарегистрировал ещё один хук** — регистрация во время прогона откладывается
  и назначает следующий проход.

**Но не бесконечно.** Цикл ограничен 10 оборотами (`MAXIMUM_REFRESH_RERUNS`), дальше в
dev-режиме летит `NG0103` с текстом «...or that afterRender hooks always mark views for check».
Хук, который грязнит что-то **безусловно, на каждом прогоне**, вешает приложение. Условно —
можно: `extra-panel` в этом репозитории пишет сигнал из хука, но только когда значение реально
изменилось, и потому сходится.

## 5. Контекст инъекции

Все три функции требуют контекст инъекции. В инициализаторе поля или в конструкторе он есть:

```ts
export class C {
  private ref = afterNextRender(() => …);   // ок
  constructor() { afterNextRender(() => …); } // ок
}
```

В `ngOnInit` его уже **нет** — нужен явный инжектор, иначе `NG0203`:

```ts
private readonly injector = inject(Injector);

ngOnInit() {
  afterNextRender(() => …, { injector: this.injector });
}
```

По умолчанию хук сам отписывается через `DestroyRef` компонента. `manualCleanup: true` это
отключает — тогда `AfterRenderRef.destroy()` на тебе (`types/core.d.ts:2284-2298`).

## 6. Что где доступно

| Точка | Доступно | Выполняется при запекании |
|---|---|---|
| конструктор | инжектор, входы **не** заполнены | да |
| `ngOnChanges` | новые значения входов | да |
| `ngOnInit` | входы заполнены; DOM компонента ещё нет | **да** |
| `ngAfterContentInit` | спроецированный контент, `@ContentChild` | да |
| `ngAfterViewInit` | `@ViewChild`, DOM создан, но кадр не отрисован | да |
| `afterNextRender` | DOM отрисован, геометрию можно мерить | **нет** |
| `afterEveryRender` | то же, после каждой отрисовки | **нет** |
| `afterRenderEffect` | то же, но только когда изменились прочитанные сигналы | **нет** |

`@ViewChild({ static: true })` доступен уже в `ngOnInit` — но только если элемент не внутри
`@if` / `@for`, то есть существует безусловно.

Правило для SSG простое: **колонка «выполняется при запекании» и есть список мест, где нельзя
принимать решения, зависящие от рантайма.**

### Оговорка про гидратацию

Все три render-функции несут в документации Angular одно и то же предупреждение:

> Components are not guaranteed to be hydrated before the callback runs.

То есть «DOM отрисован» и «гидратация закончилась» — **не одно и то же**. Хук может выполниться
на разметке, которая ещё не перехвачена Angular. Для замеров геометрии это обычно неважно, а
вот для «найду элемент и подпишусь на него» — важно: элемент может быть тем самым, который
гидратация вот-вот заменит.

## 7. `afterRenderEffect` — зачем он существует

Формально это `effect()`, выполняющийся в фазе render-хуков. Но так его выбрать нельзя —
непонятно, чем он лучше соседей. Практическое отличие в трёх свойствах, и брать его нужно
тогда, когда нужны **все три сразу**:

| | Реагирует на сигналы | Видит обновлённый DOM | `onCleanup` на каждый прогон |
|---|---|---|---|
| `effect()` | да | **нет** | да |
| `afterEveryRender` | **нет**, работает всегда | да | **нет** |
| `afterNextRender` | **нет**, один раз | да | **нет** |
| `afterRenderEffect` | да | да | да |

Ни один сосед не даёт всех трёх. Это и есть ответ на «зачем оно».

### Про `onCleanup` — то, чего нет у остальных

Каждая фаза получает функцию уборки, которая вызывается **перед следующим прогоном** (и при
уничтожении):

```ts
afterRenderEffect({
  read: (onCleanup) => {
    const el = this.target();          // сигнал: элемент меняется
    if (!el) return;

    const ro = new ResizeObserver(() => this.size.set(el.getBoundingClientRect()));
    ro.observe(el);

    onCleanup(() => ro.disconnect());  // ← снимаем старую подписку сами не думая
  }
});
```

У `afterEveryRender` этого нет вовсе: там пришлось бы отписываться руками в начале каждого
прогона и не забыть про `DestroyRef`.

### Про передачу между фазами — значение приходит `Signal`-ом

Первая фаза не получает ничего, каждая следующая получает результат предыдущей **как сигнал**,
а не как обычное значение:

```ts
afterRenderEffect({
  earlyRead: () => this.anchor()?.getBoundingClientRect() ?? null,  // ЧИТАЕМ
  write: (rect) => {                        // rect: Signal<DOMRect | null>
    const r = rect();
    if (!r) return;
    const pop = this.popup().nativeElement;
    pop.style.top = `${r.bottom}px`;        // ПИШЕМ
  }
});
```

Именно потому, что это сигнал, фаза `write` не перезапустится, если геометрия не изменилась.
С обычным значением такой экономии не было бы.

Форма без фаз (просто коллбэк) выполняется в `mixedReadWrite`, и документация Angular помечает
это как критичное для производительности — лучше всегда указывать фазу явно.

Гарантируется как минимум один запуск (`types/core.d.ts:2643`).

## 8. Два места в этом репозитории, на которых видно разницу

### Случай, который просится на `afterRenderEffect`

`virtual-scroll.component.ts:160-170` — `ResizeObserver` переподписывается на элементы внутри
обычного `effect()`:

```ts
effect(() => {
  const elements = this.itemElements();
  if (!this.resizeObserver) return;

  this.resizeObserver.disconnect();          // ← уборка руками
  for (const elRef of elements) {
    this.resizeObserver.observe(elRef.nativeElement);
  }
});
```

Три признака, что инструмент взят не тот, и все три видны прямо в коде:

1. **зависит от сигнала** — `itemElements()`;
2. **трогает DOM** — `observe()` на живых элементах, а обычный `effect()` выполняется **до**
   обновления DOM;
3. **вручную воспроизводит `onCleanup`** — `disconnect()` перед переподпиской.

Это дословное описание `afterRenderEffect` с `onCleanup`. Работает оно сейчас в основном
потому, что `ResizeObserver` сам дёргает коллбэк при `observe()`, то есть промах по времени
компенсируется поведением API. Кандидат на переписывание.

### Случай, который на `afterRenderEffect` НЕ переводится

`extra-panel.component.ts:64-95` — `afterEveryRender` с двумя `getBoundingClientRect()`,
выполняется после **каждой** отрисовки приложения, хотя интересна только смена контента:

```ts
afterEveryRender({
  mixedReadWrite: () => {
    let parentbound = subPanel.getBoundingClientRect();
    let chidBound = fullChild.getBoundingClientRect();
    let isExpandable = parentbound.height < chidBound.height;
    if (this.shouldShowExtraBtn() != isExpandable) return isExpandable;
    return undefined;
  },
  read: (writeResult) => {
    if (writeResult != undefined) this.shouldShowExtraBtn.set(writeResult);
  }
});
```

Выглядит как очевидный кандидат — но перевести его нельзя, и причина важная:
**`afterRenderEffect` перезапускается по изменению сигналов, а здесь зависимость — высота
DOM-узла, которая сигналом не является.** Никакой сигнал не «изменится», когда контент стал
выше; узнать это можно только померив после отрисовки.

`isOpenExtra` тут вдобавок обычный `@Input`, а не сигнал, так что даже частичного выигрыша не
будет.

**Вот ровно поэтому в API есть обе функции.** Зависимость выражается сигналом —
`afterRenderEffect`. Зависимость выражается только состоянием DOM — `afterEveryRender`, и это
не лень, а единственный вариант.

Побочно стоит заметить: этот хук пишет сигнал (`shouldShowExtraBtn.set`) из фазы `read`, то
есть назначает ещё один проход. Он сходится только потому, что значение ставится **лишь при
реальном изменении**. Убрать это условие — получить `NG0103` из §4.

## 9. Template / content / container — что есть что

Постоянно путаемая четвёрка. Разница чисто в том, кому принадлежит разметка.

**`<ng-template>`** — рецепт, а не разметка. Сам по себе не рендерится никогда; из него
получают `TemplateRef` и вставляют явно. Именно так работает `*ngTemplateOutlet` — тот, что
у нас в `restore-password.component.html` и `invite-register-user.component.html`.

**`<ng-container>`** — группировка без собственного DOM-узла. Нужен, когда надо навесить
директиву на кусок разметки, не заводя лишний `<div>`.

**`<ng-content>`** — точка проекции: сюда попадёт то, что родитель положил между тегами
твоего компонента. Не копирует, а **перемещает** уже созданные узлы.

**`ViewContainerRef`** — место, куда можно программно вставлять виды (`createEmbeddedView`,
`createComponent`). Физически это якорь-комментарий в DOM.

Отсюда деление запросов:

| | Что ищет | Когда готово |
|---|---|---|
| `@ViewChild` / `viewChild()` | в **моём собственном** шаблоне | `ngAfterViewInit` |
| `@ContentChild` / `contentChild()` | в том, что мне **спроецировали снаружи** | `ngAfterContentInit` |

Контент готов раньше вида, потому что он принадлежит родителю и создан до того, как дочерний
компонент начал строить свой шаблон. Отсюда и порядок хуков: `ngAfterContentInit` всегда до
`ngAfterViewInit`.

Сигнальные запросы (`viewChild()`, `contentChild()`) в этом смысле удобнее: их читают как
сигнал, и они сами уведомляют change detection при изменении — не нужно угадывать момент.

## 10. Короткий свод

- Чтобы что-то отрисовалось, кто-то должен позвать `notify` — см. парный документ.
- Мерить DOM — только в render-хуках, `ngAfterViewInit` для этого рано.
- Нужен браузер и не нужен сервер — render-хук, это единственный способ гарантированно не
  попасть в запечённый HTML.
- Всё, что делается в `ngOnInit`, случится и при запекании тоже.
- **Регистрация** хука будит отрисовку; **тело** хука само по себе ничего не грязнит. Грязнит
  только явный `markForCheck` или запись сигнала внутри.
- `afterNextRender` из обработчика или подписки — это назначенный проход, а не бесплатное
  ожидание кадра.
- `afterRenderEffect` берут, когда нужны все три свойства сразу: реакция на сигналы, свежий DOM
  и `onCleanup`. Если зависимость нельзя выразить сигналом — нужен `afterEveryRender`.
- Разложить работу по `read`/`write` дешевле, чем свалить в `mixedReadWrite`.
