# Директивы, шаблоны и контейнеры видов

Шпаргалка по Angular **21.2.16**. Примеры — из этого репозитория, все перечисленные паттерны
в нём уже живут, так что смотреть можно на рабочий код, а не на выдуманный.

Соседние документы: [angular-render-hooks.md](angular-render-hooks.md),
[angular-change-detection-zoneless.md](angular-change-detection-zoneless.md).

---

## 1. Три способа отдать разметку компоненту

Это главная развилка, из которой растёт всё остальное.

| Способ | Кто решает, когда и сколько раз рисовать | Можно ли передать данные внутрь | Пример в репо |
|---|---|---|---|
| `<ng-content>` | никто, вставляется как есть, ровно один раз | нет | `extra-panel.component.html:3` |
| `TemplateRef` через маркер-директиву | **компонент-хозяин** | да, через контекст | `ExtraPanelBtnTemplatDirective` |
| структурная директива | **сама директива** | да, через контекст | закомментированный `DogDirective` |

Ключевое различие первых двух: `<ng-content>` **перемещает** уже созданные узлы — они
создаются в момент создания родителя, один раз, и родитель не может ни отрисовать их дважды,
ни передать им данные. `TemplateRef` — это рецепт, который ещё не выполнен; хозяин решает,
когда, сколько раз и с какими данными его выполнить.

Отсюда правило выбора: **нужно нарисовать N раз или подставить свои данные — только шаблон,
`ng-content` не подойдёт.**

## 2. Паттерн «маркерная директива»: хидер, футер, кнопка

Тот самый случай «внутрь контентом передают футер и хидер в виде div, но с директивой, что
есть что». Механика в трёх шагах.

**Шаг 1. Директива-маркер, единственная задача которой — забрать `TemplateRef`.**

`extra-panel.component.ts:9-14`:

```ts
@Directive({ selector: '[appExtraPanelBtnTemplate]' })
export class ExtraPanelBtnTemplatDirective {
  constructor(public templateRef: TemplateRef<unknown>) {}
}
```

Тела нет вообще. Angular умеет инжектировать `TemplateRef` в директиву, стоящую на
`<ng-template>` — это и есть весь фокус. Директива тут работает как **типизированная метка**:
она отвечает на вопрос «какой из вложенных шаблонов чем является».

**Шаг 2. Хозяин находит её среди спроецированного контента.**

`extra-panel.component.ts:40`:

```ts
@ContentChild(ExtraPanelBtnTemplatDirective) extraBtnTemplate?: ExtraPanelBtnTemplatDirective;
```

**Шаг 3. Хозяин рисует шаблон там и тогда, когда ему удобно, подставляя свои данные.**

`extra-panel.component.html`:

```html
@if(!!extraBtnTemplate?.templateRef) {
  <ng-container [ngTemplateOutlet]="extraBtnTemplate!.templateRef"
                [ngTemplateOutletContext]="{$implicit: isOpenExtra}"></ng-container>
} @else {
  … разметка по умолчанию …
}
```

Обрати внимание на `@else`: шаблон необязателен, и хозяин подставляет своё оформление, если
пользователь ничего не передал. С `<ng-content>` так не сделать — там нельзя узнать, положили
внутрь что-нибудь или нет.

Снаружи это выглядит так:

```html
<app-extra-panel>
  <ng-template appExtraPanelBtnTemplate let-open>
    {{ open ? 'Свернуть' : 'Развернуть' }}
  </ng-template>
</app-extra-panel>
```

## 3. Контекст шаблона и `let-`

`ngTemplateOutletContext` — обычный объект. Его поля становятся переменными шаблона через
`let-имя="поле"`, а поле `$implicit` достаётся просто как `let-имя`.

Полноценный типизированный пример — виртуальный скролл. Тип контекста
(`virtual-scroll.types.ts`):

```ts
export interface VsItemContextT<T> {
  $implicit: T;
  index: number;
  first: boolean;
  last: boolean;
  even: boolean;
  odd: boolean;
}
```

Хозяин собирает его на каждый элемент (`virtual-scroll.component.ts:241-251`) и передаёт в
`*ngTemplateOutlet` вместе с шаблоном (`virtual-scroll.component.html:43`):

```html
<ng-container *ngTemplateOutlet="itemTemplateRef;
              context: itemContext(renderedRange().start + $index, item)"></ng-container>
```

### Как получить типизацию в шаблоне

Просто `TemplateRef<Ctx>` компилятору недостаточно — нужен статический
`ngTemplateContextGuard`. `virtual-scroll-item.directive.ts`:

```ts
@Directive({ selector: '[vsItemT]', standalone: true })
export class VsItemDirectiveT<T> {
  constructor(public readonly templateRef: TemplateRef<VsItemContextT<T>>) {}

  static ngTemplateContextGuard<T>(_dir: VsItemDirectiveT<T>, ctx: unknown): ctx is VsItemContextT<T> {
    return true;
  }
}
```

После этого в потребителе `let-item`, `let-i="index"` типизированы, и `strictTemplates` ловит
опечатки в именах полей. Тот же приём в общем виде — `TypedTemplateDirective`
(`directives/typedTemplateDirective.ts`).

Если контекста нет, так и пишут: `TemplateRef<void>` — см. `VsLoaderDirectiveT`.

## 4. Как хозяин находит контент: два поколения API

**Старое, декоратором:**

```ts
@ContentChild(ExtraPanelBtnTemplatDirective) extraBtnTemplate?: ExtraPanelBtnTemplatDirective;
```

Доступно с `ngAfterContentInit`, до этого `undefined`. Change detection об изменениях сама не
узнаёт.

**Новое, сигнальное** (`virtual-scroll.component.ts:88-89`):

```ts
private readonly itemDirective = contentChild(VsItemDirectiveT, { read: TemplateRef });
private readonly loaderDirective = contentChild(VsLoaderDirectiveT, { read: TemplateRef });
```

Читается как сигнал, сам уведомляет change detection — **в zoneless это заметно удобнее**, не
надо гадать про момент и звать `markForCheck`.

Опция `{ read: … }` говорит, что вернуть с найденного узла. Без неё вернётся экземпляр
директивы (и `TemplateRef` придётся доставать полем, как в `extra-panel`); с
`{ read: TemplateRef }` — сразу шаблон. Так же можно попросить `ElementRef` или
`ViewContainerRef`.

Для нескольких меток одного типа — `contentChildren()` / `@ContentChildren`.

| | Что ищет | Когда готово |
|---|---|---|
| `viewChild()` / `@ViewChild` | в **своём** шаблоне | `ngAfterViewInit` |
| `contentChild()` / `@ContentChild` | в **спроецированном снаружи** | `ngAfterContentInit` |

Контент готов раньше вида: он принадлежит родителю и создан до того, как дочерний компонент
начал строить свой шаблон.

## 5. Структурная директива: когда решает сама директива

### Если совсем коротко (читать это, остальное — доказательства)

Структурная директива **ничего не меняет в природе шаблонов**. Шаблон как был пассивным куском
разметки, так и остался: сам себя он не издаёт и издавать не научился.

Весь трюк в том, что директиву-то движок обязан создать и исполнить — она объявлена в разметке,
селектор совпал. И вот она, исполняясь, делает ровно ту же работу, что делал бы
`*ngTemplateOutlet`: материализует шаблон. Разница одна — она делает это **на том же
комментарии**, который уже стоит на месте объявления, а не заводит новый.

Как звери, которые нор не роют, а въезжают в готовые.

Нору выкопал не шаблон и не директива, а инструкция `ɵɵtemplate` — просто потому что в
разметке был `<ng-template>` (пусть и появившийся из звёздочки). Директива въехала и стала
единственным жильцом, который что-то делает.

Проверка на пассивность: `<ng-template>Гав</ng-template>` без единой директивы не отрисует
ничего и никогда. Комментарий будет, `Гав` — нет. Некому исполнить.

### Поправка к аналогии: не `ng-content`, а `ngTemplateOutlet`

Соблазнительно сказать «директива копирует механизм `ng-content`» — но это разные механизмы,
и разница практическая:

| | Что делает | Сколько раз |
|---|---|---|
| `<ng-content>` | **перемещает** уже созданные узлы родителя | ровно один: узлы одни |
| `createEmbeddedView` | **создаёт** узлы по рецепту | сколько угодно, `*ngFor` на этом и стоит |

`ng-content` не создаёт `LContainer`, не даёт `TemplateRef` и не умеет повторить проекцию
дважды. Правильный аналог — `ngTemplateOutlet`. Насколько правильный, видно по исходникам
`@angular/common`: это буквально один и тот же вызов.

```js
// NgIf, _common_module-chunk.mjs:1835 и :1861
constructor(_viewContainer, templateRef) { … this._thenTemplateRef = templateRef; }
this._thenViewRef = this._viewContainer.createEmbeddedView(this._thenTemplateRef, this._context);

// NgTemplateOutlet, :2405 и :2419
constructor(_viewContainerRef) { … }          // TemplateRef НЕ инжектится
this._viewRef = viewContainerRef.createEmbeddedView(this.ngTemplateOutlet, viewContext, …);
```

Отличий по существу два, и оба про «откуда взялись рецепт и место»:

- **`NgIf` инжектит `TemplateRef` из своего хоста** — потому шаблон и рисуется по месту;
- **`NgTemplateOutlet` получает его входом** — потому и рисует чужой шаблон у себя.

Всё остальное — одинаково. `NgSwitch` там же (`:1943-1958`) устроен так же, через
`SwitchView.create()` / `destroy()`.

### Так выглядит своя такая директива

Здесь она получает **две** вещи — шаблон и место, куда его можно вставить:

```ts
@Directive({ selector: '[isDog]', standalone: true })
export class DogDirective {
  @Input('isDog') set isDogInput(animal: Animal) {
    if (isDog(animal.type)) {
      this.viewContainerRef.createEmbeddedView(this.templateRef);
    } else {
      this.viewContainerRef.clear();
    }
  }

  constructor(
    private readonly viewContainerRef: ViewContainerRef,
    private readonly templateRef: TemplateRef<unknown>
  ) {}
}
```

(лежит закомментированным в `directives/typedTemplateDirective.ts:17-33`)

### Как `<ng-template>` находит себе якорь: он его не находит

Главный вопрос, на котором ломается интуиция: шаблон вроде бы «рецепт, который вставится там,
где его позовут» — откуда же он знает, куда рисоваться при `*isDog`? Ответ: **якорь появляется
раньше директивы и вообще независимо от неё**, а `TemplateRef` и `ViewContainerRef` — это две
проекции одного и того же места.

Разберём по инструкциям рантайма. `*isDog="animal"` компилируется в `ɵɵtemplate(...)` — вызов,
стоящий в шаблоне родителя **на той позиции, где ты написал звёздочку**. Дальше
`declareDirectiveHostTemplate` (`_debug_node-chunk.mjs:10296-10315`) делает три вещи строго в
таком порядке:

```js
templateCreate(tNode, declarationLView, ...);      // :10308  ← якорь и контейнер
if (isDirectiveHost(tNode)) {
  createDirectivesInstances(declarationTView, ...); // :10310  ← только теперь конструктор директивы
}
```

А `templateCreate` (`:10273-10295`) — вот он целиком по сути:

```js
const comment = _locateOrCreateContainerAnchor(...);          // :10286 → createComment('container'), :10355
if (wasLastNodeCreated()) appendChild(tView, lView, comment, tNode);  // :10288 ← комментарий В DOM
const lContainer = createLContainer(comment, lView, comment, tNode);  // :10291
lView[index + HEADER_OFFSET] = lContainer;                            // :10292 ← в слот
```

Отсюда три факта, каждый из которых противоречит «естественному» ожиданию:

1. **`<ng-template>` оставляет в DOM комментарий ровно там, где объявлен** (`:10288`). Он не
   исчезает без следа. Исчезает его **содержимое** — а место остаётся помеченным.
2. **Контейнер вставки создаётся тем же вызовом** и кладётся в слот `LView` (`:10292`) — до
   того, как хоть одна директива инстанцирована.
3. **Директива ничего себе не определяет.** Она инжектит `ViewContainerRef`, а
   `createContainerRef` (`:9109-9121`) первым делом смотрит в слот:

```js
const slotValue = hostLView[hostTNode.index];
if (isLContainer(slotValue)) {
  lContainer = slotValue;        // ← случай <ng-template>: берём готовое, новых узлов ноль
} else { … }
```

То есть **`TemplateRef` и `ViewContainerRef` у структурной директивы указывают на один и тот же
`TNode`**: первый — «что рисовать», второй — «куда». Оба взяты из позиции звёздочки. Никакого
поиска, никакой магии: точка объявления **и есть** точка вставки.

Поэтому `*ngIf` рисует по месту, а не куда-то в конец body.

### Три хоста `ViewContainerRef` — и они ведут себя по-разному

`createContainerRef` начинается с `assertTNodeType(hostTNode, 12 | 3)` (`:9110`), то есть биты
`Text|Element|Container|ElementContainer` (нумерация — `toTNodeTypeAsString`, `:598-609`). Дальше
всё решает `createAnchorNode` (`:9136-9145`):

| Хост директивы | Что делает рантайм | Где окажутся виды |
|---|---|---|
| `<ng-template>` (тип 4) | `LContainer` уже в слоте — **переиспользуется**, новых узлов ноль | после комментария шаблона |
| `<ng-container>` (тип 8) | `LContainer` создаётся, но якорь — **собственный комментарий** ng-container (`unwrapRNode(slotValue)`, `:9140`) | после этого комментария |
| `<div>` (тип 2) | `LContainer` создаётся + **новый** комментарий (`:9142`) | после `<div>`, снаружи него |

Последняя строка — не догадка, а буквальный `insertAnchorNode` (`:9123-9130`):

```js
const commentNode = renderer.createComment(ngDevMode ? 'container' : '');
const hostNative = getNativeByTNode(hostTNode, hostLView);
nativeInsertBefore(renderer, renderer.parentNode(hostNative),
                   commentNode, renderer.nextSibling(hostNative), false);
```

`nextSibling(hostNative)` — вот доказательство того, что вставка идёт **соседом после хоста, а
не внутрь него**:

```html
<div [someDir]="x">содержимое дива</div>
<!-- якорь someDir здесь, и всё вставленное появится следом -->
```

Так что `<ng-container someDir>` — вполне законный хост контейнера, просто он экономит один
узел: свой комментарий он и отдаёт под якорь.

### `TemplateRef` — только на шаблоне

`createTemplateRef` (`:6243-6249`):

```js
if (hostTNode.type & 4) {  // Container, т.е. <ng-template>
  return new TemplateRef(hostLView, hostTNode, createElementRef(hostTNode, hostLView));
}
return null;
```

На `<div>` возвращается `null`, а `null` из спец-фабрики в NodeInjector — это
`throwProviderNotFoundError` (`:932-933`), то есть `RuntimeError(-201)` = **`NG0201: No provider
for TemplateRef`** (`_effect-chunk2.mjs:576-578`). Поэтому структурную директиву нельзя написать
атрибутом на элементе: `ViewContainerRef` она получит, а `TemplateRef` — нет.

Кстати, `elementRef` у `TemplateRef` — это тот самый комментарий-якорь. Проверяется в одну
строку: `tpl.elementRef.nativeElement.nodeType === 8`.

### Звёздочка — сахар над всем этим

```html
<!-- пишешь -->
<div *isDog="animal">Гав</div>

<!-- компилятор разворачивает в -->
<ng-template [isDog]="animal">
  <div>Гав</div>
</ng-template>
```

В DOM:

```
условие ложно:     <!---->
условие истинно:   <!---->
                   <div>Гав</div>
```

Вставка соседом нужна именно затем, чтобы директива могла удалить сам `<div>`: он снаружи
якоря, а не внутри. В прод-сборке текст комментария вырезан (`createComment(ngDevMode ?
'container' : '')`) — в `dist/.../signin/index.html` таких якорей 82 штуки в виде `<!---->`;
в дев-режиме там читаемое `container`. При гидрации якорь не создаётся, а **отыскивается** в
пришедшем с сервера HTML (`locateOrCreateContainerAnchorImpl`, `:10357`) — потому SSR-разметка
эти комментарии и обязана содержать.

`<ng-container>` в разворачивании звёздочки **не участвует** — компилятор его туда не
подставляет. Это отдельный инструмент: навесить директиву или `@if` на кусок разметки, не
заводя лишний `<div>`. Пересечение с темой ровно одно — он тоже представлен комментарием, и
из-за этого его постоянно склеивают с якорем контейнера.

### Где интуиция «шаблон рисуется там, где его позовут» всё-таки верна

Она верна для **другого** случая — когда `<ng-template #tpl>` объявлен в одном месте, а
отрисован в другом (`*ngTemplateOutlet`, передача `TemplateRef` во входе — как у нас в
`ExtraPanelBtnTemplatDirective`, §2). Тогда комментарий на месте объявления остаётся, но рядом
с ним так ничего и не появляется, а содержимое возникает у аутлета. Отсюда и ощущение, что
шаблон «изымается из разметки».

Важная деталь при этом: вид строится против **декларационного** `LView`, а не того, куда его
вставили — `createEmbeddedViewImpl` передаёт `this._declarationLView, this._declarationTContainer`
(`:6232-6237`). Практическое следствие: пайпы, DI и контекст шаблон берёт **оттуда, где
написан**, а позицию в DOM — оттуда, куда вставлен. Это две независимые вещи, и путаница между
ними — источник багов вида «пайп не найден, хотя он импортирован в том компоненте, где я вижу
разметку».

Сегодня своё `*ngIf` писать почти никогда не надо — есть `@if` / `@for`. Структурная директива
остаётся оправданной, когда нужна логика, которой во встроенном control flow нет: права
доступа, feature-флаги, отложенная загрузка по своим правилам.

## 6. `ViewContainerRef` — что реально можно

Проверено по `node_modules/@angular/core/types/core.d.ts:3629-3720`:

```ts
createEmbeddedView<C>(templateRef: TemplateRef<C>, context?: C, index?: number): EmbeddedViewRef<C>
createComponent<C>(componentType: Type<C>, options?): ComponentRef<C>
insert(viewRef: ViewRef, index?: number): ViewRef
move(viewRef: ViewRef, currentIndex: number): ViewRef
indexOf(viewRef: ViewRef): number
remove(index?: number): void        // уничтожает вид
detach(index?: number): ViewRef     // вынимает, НЕ уничтожая
clear(): void
get(index: number): ViewRef | null
get length(): number
get element(): ElementRef
get injector(): Injector
```

Главное различие, на котором спотыкаются: **`remove()` уничтожает вид, `detach()` — нет.**
`detach` + `insert` = перенос вида в другое место с сохранением состояния. `remove` + создание
заново = потеря всего локального состояния.

`createComponent` — динамическое создание компонента; `options` принимает свой `injector`, так
что можно подсунуть созданному компоненту отдельные провайдеры.

## 7. Директива, которая пишет в свой хост

Второй большой класс — не «принести разметку», а «изменить элемент, на котором я стою».

**Через `ElementRef` + `Renderer2`** — `directives/highlight-content-directive.ts:16`:

```ts
constructor(private el: ElementRef, private renderer: Renderer2) { }
```

`ElementRef.nativeElement` даёт прямой доступ к DOM-узлу. Работает, но убивает SSR: на сервере
`nativeElement` не настоящий DOM. `HighlightContentDirective` пишет `innerHTML` напрямую — с
пререндером это несовместимо, помни об этом, если такая директива окажется на запекаемом
роуте.

**Через host-биндинги** — декларативно, работает и на сервере.
`extra-panel.component.ts:21-24`:

```ts
host: {
  '[style.height]': "isOpenExtra ? 'max-content !important' : 'calc(…)'",
  '[style.max-height]': "reduceToMaxContent ? 'max-content' : undefined"
}
```

Правило простое: **что можно выразить host-биндингом — выражать host-биндингом.** `ElementRef`
оставить для того, что действительно требует императивного DOM (замеры, сторонние библиотеки),
и держать это в render-хуках, а не в `ngOnInit` — см.
[angular-render-hooks.md](angular-render-hooks.md).

## 8. Обмен данными с директивой

**Снаружи внутрь — входы.** Сигнальные предпочтительнее
(`highlight-content-directive.ts:139`):

```ts
public hContent = input<string | (string | SafeString)[] | undefined>('hContent');
private hContentProcessed = computed(() => { … });
```

Вычисляемое от входа делается через `computed` и не требует ни `ngOnChanges`, ни
`markForCheck`. Старый стиль в этом же файле — `@Input() hPattern` плюс `ngOnChanges`, который
руками зовёт `updateInnerHtml()`. Разница наглядная.

**Изнутри наружу — выходы:** `public hasFilter = output<boolean>()` (строка 168).

**Хозяин читает свойства найденной директивы.** Это и есть третий вариант из твоего вопроса —
`extra-panel` берёт `extraBtnTemplate.templateRef` у найденной через `@ContentChild` директивы.
Можно так же прочитать любые её входы: пользователь навесил `<div appCardHeader [sticky]="true">`,
а хозяин через `@ContentChild(CardHeaderDirective)` читает `.sticky` и рисует по-своему.

**Хозяин пишет в найденную директиву.** Тоже законно, но обязательно в
`ngAfterContentInit`/позже, и это классический источник `ExpressionChangedAfterItHasBeenChecked`
в zone-режиме. С сигнальными запросами и сигнальными входами проблема снимается: запись в
сигнал сама планирует проход.

## 9. Как понять, что нужна директива, а не компонент

Самая трудноуловимая развилка: со структурными и маркерными всё более-менее очевидно, а вот
момент «стоп, тут нужна директива» на обычной задаче ловится плохо. Ниже — решето и разбор
реального случая из этого репозитория.

### Определяющее различие

**Компонент приносит свою разметку. Директива приходит к чужой.**

Это не стилистика, а определение: у `@Directive` нет и не может быть `template` и `styles`.
Если тебе есть что показать — ты компонент. Если тебе нечего показать, но есть что сделать с
уже показанным — ты директива.

### Правило, которое закрывает половину случаев без раздумий

На одном элементе может быть **максимум один компонент**, но **сколько угодно директив**.

Отсюда: если место уже занято чужим компонентом — обсуждать нечего, только директива. В этом
репозитории таких использований 20 штук, и все три «поведенческие» директивы живут ровно там:

| Директива | Хост | Почему не компонент |
|---|---|---|
| `rowDblClick` | `<kendo-grid>` | слот компонента занят Kendo |
| `overlayClick` | `<kendo-dialog>` | то же; плюс слушает `.k-overlay`, узел не наш |
| `debounceValueChanged` | `<kendo-textbox>` | то же; слушает `valueChange` чужого компонента |

### Налог на обёртку

Соблазн «оберну в свой компонент» стоит дорого, и цену видно заранее:

- **переобъявить все входы и выходы** оборачиваемого. У `<kendo-grid>` их десятки, и каждый
  новый в апдейте библиотеки — твоя работа. У директивы этот налог равен нулю;
- **лишний узел ломает CSS библиотеки.** Селекторы вида `.k-grid-content > tr` перестают
  совпадать, потому что между ними встал твой тег;
- **в таблицу свой тег вообще не вставить.** Между `<table>` и `<tr>` чужого элемента быть не
  может — браузер его выкинет. Здесь директива не «удобнее», а единственный вариант.

### Решето (по порядку, первый сработавший ответ и есть ответ)

1. **Есть своя разметка, которую надо показать?** Да → компонент, дальше не читаем.
2. **Место занято чужим компонентом или свой тег вставить нельзя** (`<tr>`, `<option>`,
   таблица, чужой оверлей)? → директива, вынужденно.
3. **Должен ли вызывающий сохранить контроль над тегом, классами, позицией в потоке текста?**
   → директива.
4. **Вешать на разные теги** (`<span>`, `<div>`, `<td>`)? → директива; компонент фиксирует тег.
5. **Комбинировать несколько таких поведений на одном элементе?** → директива.
6. **Нужны изолированные стили?** → компонент, у директивы их нет.

### Реконструкция: почему `highlightContent` стал директивой

Случай нарочно взят пограничный — потому он сразу и не дался.

Как оно используется (`cashboxes-card.component.html`, 9 мест):

```html
ЗН: <span highlightContent [hEnabled]="filterEnabled" [hPattern]="filterStr"
          [hContent]="cashBox.devDto.serial" (hasFilter)="filterMatch($event, false)"></span>
(ИНН <span highlightContent … [hContent]="…fiscalRegistration?.inn ?? noDatatxt"></span>)
<span class="ws-pre-wrap-anywhere" highlightContent …></span>
```

Что здесь решает:

- **Использование инлайновое, посреди текста.** `ЗН: <span…>`, `(ИНН <span…>)`. Компонент
  вставил бы в поток свой тег, и вёрстка стала бы его заботой, а не вызывающего.
- **Класс висит на том же элементе:** `class="ws-pre-wrap-anywhere"`. Вызывающий управляет
  оформлением, директива — содержимым. У компонента класс сел бы на хост, а текст оказался
  внутри, и `white-space` пришлось бы прокидывать вручную.
- **Девять мест — девять разных полей DTO.** Общего между ними нет ничего, кроме поведения.
  Общее поведение при разных данных — это ровно определение директивы.
- **Решающее: она пишет `innerHTML` хоста.** Компонент своим `innerHTML` не распоряжается — он
  рендерит свой шаблон. Чтобы выдать из компонента вычисленный HTML, нужен `[innerHTML]` плюс
  обход санитайзера.

Археологическое доказательство, что этот путь пробовался и был отвергнут: в файле на строке 2
висит `import { DomSanitizer } from "@angular/platform-browser";` — **и он нигде не
используется**. Так и выглядит след от варианта с `[innerHTML]` + `bypassSecurityTrust`.

**Почему не пайп** (а это первый инстинкт на «преобразовать текст»): пайп не может вернуть
HTML без `[innerHTML]` на месте вызова и санитайзера, и главное — **у пайпа нет выходов**, а
здесь наружу летит `(hasFilter)`, по которому карточка решает, показывать ли себя вообще.

Формулировка, до которой тогда дошли молча: подсветка — это не «что показать», а «как показать
то, что уже сказано». Первое — компонент, второе — директива.

### Почему этот случай был неочевидным

Есть две оси владения, и обычно они совпадают:

| | Кто владеет элементом | Кто владеет содержимым |
|---|---|---|
| компонент | он сам | он сам |
| обычная директива (`rowDblClick`) | вызывающий | вызывающий |
| `highlightContent` | вызывающий | **директива** |

`highlightContent` — гибрид: содержимое его, элемент чужой. Отсюда и заминка: по содержимому он
похож на компонент. Такое законно, пока элемент остаётся вызывающего — назовём это
директивой-форматтером. Как только захочется ещё и свой тег — пора превращаться в компонент.

### Проверочный вопрос

> Если убрать директиву из разметки — что останется?

Осмысленный рабочий элемент без фичи → директива была верным выбором (`<kendo-grid>` без
`rowDblClick` — обычный грид). Пустое место или бессмыслица → надо было делать компонент.
`highlightContent` этот тест проходит наполовину — что и подтверждает: он гибрид, а не эталон.

### Запахи

| Что слышится в голове | Что нужно |
|---|---|
| «копирую один и тот же `(click)` в пятый шаблон» | директива поведения |
| «нужен нативный элемент, а у меня его нет» | директива |
| «обёртка ломает вёрстку или API библиотеки» | директива вместо обёртки |
| «надо прокинуть 12 входов насквозь» | директива |
| «хочу писать в элемент, но элемент не мой» | директива |
| «мне нужна метка, а не разметка» | маркерная директива (§2) |
| «решаю, рисовать ли вообще» | структурная (§5) |
| «у меня 20 строк вёрстки» | компонент |
| «нужен изолированный стиль» | компонент |
| «нужна своя внутренняя структура с `ng-content`» | компонент |

## 10. Что выбирать

| Задача | Инструмент |
|---|---|
| просто вставить разметку внутрь, один раз | `<ng-content>` |
| нарисовать переданное N раз / со своими данными | маркер-директива + `TemplateRef` + `ngTemplateOutlet` |
| несколько именованных слотов (хидер, футер) | по маркер-директиве на слот + `contentChild` на каждый |
| решение «рисовать или нет» принимает переданная логика | структурная директива |
| нужен `@if` / `@for` | встроенный control flow, не самопал |
| изменить элемент, на котором стою | host-биндинги; `ElementRef` только если иначе никак |
| создать компонент во время работы | `ViewContainerRef.createComponent` |
| перенести вид, сохранив состояние | `detach()` + `insert()`, **не** `remove()` |

## 11. Грабли

- **`@ContentChild` не найдёт то, что лежит внутри `@if`/`@for`,** пока условие ложно. Для
  сигнальных запросов это нормально — вернётся `undefined` и обновится позже; для декоратора
  надо не забыть, что значение может появиться после `ngAfterContentInit`.
- **`static: true` работает только для безусловной разметки.** Внутри `@if` — всегда `false`.
- **`ng-content` нельзя «использовать дважды».** Второй `<ng-content>` с тем же селектором
  оставит первый пустым: узлы перемещаются, а не копируются.
- **`ElementRef.nativeElement` на сервере не настоящий DOM.** Директива, которая пишет туда в
  `ngOnInit`, ломает пререндер молча.
- **`TemplateRef` без `ngTemplateContextGuard` не типизирован.** `let-item` будет `any`, и
  опечатка в имени поля контекста пройдёт мимо `strictTemplates`.
- **`remove()` вместо `detach()`** уничтожает вид со всем состоянием — форма, скролл, фокус.
- **Первый аргумент `input()` — значение по умолчанию, а не алиас.** В
  `highlight-content-directive.ts:139` написано `input<…>('hContent')`, то есть значение по
  умолчанию — строка `'hContent'`. Сейчас не стреляет: все 9 использований биндят `[hContent]`.
  Но `<span highlightContent>` без биндинга покажет буквальный текст `hContent`. Алиас
  задаётся вторым аргументом — `input(undefined, { alias: … })` — и здесь он вообще не нужен,
  имя поля уже совпадает.
