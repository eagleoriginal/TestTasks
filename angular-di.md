# DI в Angular

## 1.1. Единица регистрации

Кусок из проекта, где видно всё сразу:

```ts
export function provideRenderStableZone(): EnvironmentProviders {   // utils/render-stable-zone.ts:57
  return makeEnvironmentProviders([
    RenderStableNgZone,                                    // (1) голый класс
    { provide: NgZone, useExisting: RenderStableNgZone },  // (2) объект
    provideEnvironmentInitializer(() => {                  // (3) вызов функции
      const zone = inject(RenderStableNgZone);
      const injector = inject(Injector);
      afterEveryRender(() => zone.emitStable(), { injector });
    }),
  ]);
}
```

Один массив, три элемента, три **разные формы записи** — и все три делают одно и то же:
регистрируют. Массив `providers` неоднороден по виду и однороден по смыслу, отсюда
и ощущение, что регистрация размазана и склеить её не за что.

Склеивать надо вот за что: **единица регистрации — один элемент такого массива**,
и в каждом элементе, какой бы формы он ни был, лежат одни и те же три вещи.

| Элемент | Ключ — что просят | Рецепт — как создать | Область — где лежит |
|---|---|---|---|
| `RenderStableNgZone` | сам класс | `new RenderStableNgZone()` | этот массив |
| `{ provide: NgZone, useExisting: RenderStableNgZone }` | `NgZone` | «отдай готовый по ключу `RenderStableNgZone`» | этот массив |
| `provideEnvironmentInitializer(fn)` | `ENVIRONMENT_INITIALIZER` (multi) | `useValue: fn` | этот массив |
| `@Injectable({ providedIn: 'root' })` на классе | сам класс | `new` этого класса | корневой массив |

Четыре строки — четыре разных синтаксиса и одни и те же три колонки. Это и есть те самые
три оси: **ключ поиска, рецепт, область видимости**. Больше в DI ничего нет.

### Главное правило: последний выигрывает - полезно когда надо `переопределить регистрацию`.

Один токен — одно значение. **Регистрация того же ключа перекрывает предыдущую,
побеждает последняя по порядку.** 

Строка `{ provide: NgZone, useExisting: RenderStableNgZone }` — ровно это:
`NgZone` уже зарегистрирован самим Angular (при zoneless-бутстрапе — как `NoopNgZone`),
а `provideRenderStableZone()` подмешивается в конфиг позже (`main.ts:29`) и перебивает
регистрацию. Никакого «слияния» не происходит — прежний рецепт просто перестаёт
использоваться.

Исключение одно: `multi: true` — тогда регистрации
не заменяют друг друга, а копятся в массив, и `inject(TOKEN)` отдаёт список.

### Что за объект `{ provide: ..., use...: ... }`

Литерал с фиксированной грамматикой. Полная форма сверху, сокращения снизу:

```
providers: [ … ]                       массив; один элемент = одна регистрация
│
├─ { provide: КЛЮЧ, РЕЦЕПТ, multi?: true }         полная форма — объект
│  │
│  ├─ provide: КЛЮЧ                    что просят
│  │  ├─ класс                         NgZone, Store, healthLkService   ← 90% случаев
│  │  ├─ InjectionToken<T>             LOCALE_ID, HTTP_INTERCEPTORS
│  │  └─ 'строка'                      легаси, не использовать
│  │
│  ├─ РЕЦЕПТ                           ровно один из четырёх
│  │  ├─ useClass:    Foo              new Foo(); аргументы конструктора соберёт сам
│  │  ├─ useExisting: Foo              не создавать — отдать готовый по ключу Foo
│  │  ├─ useValue:    любое            не создавать — отдать это как есть
│  │  └─ useFactory:  fn               позвать fn(...deps) и отдать результат
│  │     └─ deps: [A, B]               обязателен: у функции нет метаданных типов
│  │
│  └─ multi: true                      не заменять прежнее, а дописать в массив
│
├─ provideXxx(…)                       функция; возвращает такие же объекты, упакованные
│  ├─ makeEnvironmentProviders([…])    запечатать массив: «только приложение/роут, не компонент»
│  ├─ provideAppInitializer(fn)        = { provide: APP_INITIALIZER,         useValue: fn, multi: true }
│  ├─ provideEnvironmentInitializer(fn)= { provide: ENVIRONMENT_INITIALIZER, useValue: fn, multi: true }
│  └─ importProvidersFrom(NgModule)    вытащить провайдеры из старого NgModule
│
└─ Foo                                 голый класс = { provide: Foo, useClass: Foo }


то же, но записанное со стороны класса, а не массива:

@Injectable({ providedIn: 'root' })    = Foo, вписанный в корневой массив
```

Ключ и рецепт в сокращённых формах совпадают — поэтому в 90% кода видно только имя класса.
Объект появляется там, где они расходятся.

### `EnvironmentProviders` и два токена-хука

```
Provider                  элемент массива: класс или { provide, use… }

Provider[]                массив элементов; вложенные массивы плющатся рекурсивно,
                          поэтому вложение и ...spread работают одинаково

makeEnvironmentProviders([…]):EnvironmentProviders   Пришивает бирку к массиву провайдеров, никого не регистрирует.
                          Фактически возвращается 
                          InternalEnvironmentProviders = { ɵbrand, ɵproviders }.
                          ЧТО ДАЁТ: такой тип не зарегистрировать в
                          @Component({ providers }) — там в сигнатуре Provider[],
                          бирка под неё не подходит. Принимают только
                          ApplicationConfig.providers и Route.providers.
                          ЧЕГО НЕ ДАЁТ: Бирка на пачке, не на провайдерах которые туда передавались. 
                          { provide: NgZone, useExisting: … } по отдельности
                          спокойно вписываются в компонент и молча дают свой NgZone
                          на каждый экземпляр.
                          ЗАЧЕМ ТОГДА: если provideXxx()
                          вернул EnvironmentProviders — в одном неправильном месте
                          будет ошибка компиляции. 

APP_INITIALIZER           multi-токен-ХУК: Angular сам забирает из DI весь список
provideAppInitializer(fn)   колбэков и зовёт их при бутстрапе, ДО первого рендера.
                          Колбэк вернул Promise/Observable — бутстрап ждёт его.
                          Внутри колбэка inject() легален.
                          Зачем: загрузить сессию/конфиг до появления UI.

ENVIRONMENT_INITIALIZER   multi-токен-ХУК: тот же механизм, другой момент —
provideEnvironmentInitializer(fn)   при создании инжектора. Раньше APP_INITIALIZER,
                          синхронно, ничего не ждёт.
                          Зачем: подпереть инфраструктуру до того, как её попросят.
```

Почему эти два вообще существуют: DI ленив — объект не создаётся, пока его кто-нибудь
не попросит. Сервис с побочным эффектом может не запуститься никогда. Эти два токена —
единственное место, где **просит сам Angular**, в заранее известный момент. Отсюда всё
их применение в проекте: дёрнуть фоновые сервисы, которых иначе никто не инжектит
(`identityInitializer.ts:14`, `connection-status-service.ts:102`,
`render-stable-zone.ts:61`).

Если переводить на .NET:

| Angular | .NET |
|---|---|
| `{ provide: X, useClass: Y }` | `services.AddSingleton<IX, Y>()` |
| `provideHttpClient()`, `provideStore()` | extension-метод `services.AddHttpClient()` |
| `provideAppInitializer(fn)` | `IHostedService.StartAsync` до приёма трафика |
| `@Injectable({ providedIn: 'root' })` | атрибут на классе, регистрирующий его синглтоном |

Разница по сути одна: в .NET контейнер один и собирается вызовами, в Angular инжекторов
дерево, а регистрация — данные, а не вызовы.

## 1.2. `InjectionToken`

Ключом почти всегда служит класс — он существует в рантайме, и сравнение идёт по ссылке.
Отсюда границы: **`interface` ключом быть не может** (стирается при компиляции, сравнивать
не с чем), `type` и дженерик — тоже; `inject(Repo<User>)` невозможен, в рантайме есть
только `Repo`. Нужен контракт без класса — либо абстрактный класс, либо токен.

`InjectionToken` нужен там, где класса нет вообще: значение — объект настроек, строка,
число, функция. Тип ключом тут не работает: у `string` нет идентичности, все строки
в приложении — один и тот же тип.

```ts
export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL');
```

- `new InjectionToken(...)` создаёт **обычный объект**, вся работа которого — существовать
  в единственном экземпляре;
- **уникальность по ссылке.** Два токена с одинаковой строкой `'API_BASE_URL'` — два
  **разных** ключа. Строка нужна только чтобы попасть в текст ошибки
  `NG0201: No provider for API_BASE_URL`. Поэтому токен — импортируемая `const`:
  важен объект, а не имя;
- **`<T>` в рантайме не существует.** Дженерик стирается и нужен только компилятору:
  чтобы `inject(API_BASE_URL)` вывелся как `string`, а
  `{ provide: API_BASE_URL, useValue: 42 }` не собрался. В реестр инжектора ложится
  голый объект-токен, типа там нет.

Токен ничего не содержит и сам не инжектируется — инжектируется то, что по нему
провайдено. Он пуст и снаружи, и внутри.

### Зачем `factory`, если рецепт и так передаётся отдельно

```ts
export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL', {
  providedIn: 'root',
  factory: () => '/api',
});
```

Это **ровно то же самое, что `@Injectable({ providedIn: 'root' })` на классе**:
ключ несёт свой рецепт при себе и сам вписывается в корневой массив. У класса рецепт
подразумевается (`new` этого класса) и писать его не надо; у токена подразумевать нечего —
из пустого ключа объект не сделаешь, — поэтому рецепт пишется явно, и называется он
`factory`.

Дальше работает обычное перекрытие: если кто-то положит `{ provide: API_BASE_URL,
useValue: 'https://api.example.com' }` в `providers`, победит он — регистрация в массиве
перекрывает дефолт, вшитый в ключ. Без `factory` токен остаётся голым ключом, рецепта
нет нигде, и первый же `inject()` даёт `NG0201`.

Побочный эффект: с `factory` токен **tree-shakable** — не инжектят, и он вместе с фабрикой
выпадает из бандла.
    
## Почему инициализаторы в `main.ts`, а не в `app.config.ts`

Это SSR-разделение, и оно уже задокументировано в коде (`main.ts:22-26`, `app.config.ts:19-26`):

- **`app.config.ts`** — универсальные провайдеры, нужные чтобы *отрисовать* приложение:
  роутер, http, store, анимации, гидрация, zoneless CD. Их же использует
  `app/app.config.server.ts` (через `main.server.ts:4`) при build-time prerender.
- **`main.ts`** — браузер-онли: фоновые таймеры (трогают `window`), SignalR-соединение,
  service worker, `provideRenderStableZone()`.

Если фоновые таймеры положить в общий `appConfig`, они **запустятся во время prerender**
на этапе сборки: сборка попробует открыть SignalR-соединение и никогда не завершится.
Поэтому разделение — не стилистика, а необходимость.

## 1.8. `inject()` vs конструктор

Функция `inject()` работает **только в инъекционном контексте**. Контекст есть:

- в конструкторе класса, создаваемого DI;
- в инициализаторе поля класса (`private x = inject(X)`) — потому что он исполняется в конструкторе;
- в `useFactory`;
- в `provideAppInitializer` / `provideEnvironmentInitializer`;
- внутри `runInInjectionContext(injector, () => ...)`;
- в функциональных гардах/резолверах/интерцепторах роутера.

Контекста **нет** в: `setTimeout`, `.subscribe()`, обработчике события, `async`-коде
после первого `await`, любом колбэке, вызванном позже. Там `inject()` падает с:
