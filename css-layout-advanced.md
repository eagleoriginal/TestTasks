# Разметка: тонкости

Продолжение `css-layout.md`. Здесь то, что кусается на практике: как grid на самом деле
считает колонки, инлайновый бокс и вертикальное выравнивание, переносы текста,
и чем отличаются способы измерить элемент.

# GRID: как считается число колонок

Главное правило, из которого следует всё остальное:

> **Число повторений в `repeat(auto-fill | auto-fit, …)` считается по МАКСИМУМУ трека,
> если он определённый, и по минимуму, если нет.**

```css
repeat(auto-fit, minmax(60px, 1fr))    /* 1fr неопределённый → считает по 60px */
repeat(auto-fit, minmax(60px, 80px))   /* 80px определённый  → считает по 80px */
```

Отсюда два совершенно разных поведения при одинаковом с виду синтаксисе.

## `auto-fill` — треки создаются и остаются

Контейнер 800px, `column-gap: 5px`, `minmax(60px, 1fr)`:

```
1. сколько влезет по минимуму:   800 / (60 + 5) = 12.3  →  12 треков
2. место под gap:                11 × 5 = 55px
3. на треки:                     800 − 55 = 745px
4. каждый трек:                  745 / 12 ≈ 62px
```

Пустые треки **остаются** и занимают место. `auto-fill` = «заполнить сетку треками»,
а не «сжать ненужные».

## `auto-fit` — пустые треки схлопываются

Тот же расчёт, но после размещения элементов **пустые треки получают размер 0**, и
прилегающие к ним гэпы схлопываются в один. Оставшееся место делится между непустыми.

Практический итог: при `1fr` пять карточек в контейнере на 12 треков растянутся на всю
ширину. При фиксированном максимуме (`minmax(60px, 80px)`) — не растянутся: колонки
упрутся в 80px, а справа останется дырка. Растяжение даёт именно `1fr`, не `auto-fit`.

## Линия `-1` — конец ЯВНОЙ сетки, не последняя колонка

Ловушка, которая выглядит мистикой:

```html
<div class="grid-element" style="grid-row: 2; grid-column: 9/11">6</div>
<div class="grid-element" style="grid-row: 2; grid-column: -2/-1">7</div>
```

```css
.grid { display: grid; column-gap: 5px;
        grid-template-columns: repeat(auto-fit, minmax(60px, 80px)); }
```

Пока все дети помещаются в посчитанные треки, `-2/-1` стоит последним. Но стоит ребёнку
запросить колонку за пределами сетки (например `13/15`), как:

- создаются **неявные** треки справа;
- `-1` по-прежнему указывает на конец **явной** сетки, то есть на 12-ю колонку;
- элемент с `-2/-1` оказывается **не последним** — правее него висят те самые неявные треки;
- места явным трекам становится меньше, они жмутся к своему минимуму;
- если и этого не хватит, сетка уедет вправо и появится горизонтальный скролл
  (гэпы никуда не деваются, даже когда треки сжаты в ноль).

Расширь окно так, чтобы явных треков стало ≥ 15 — и всё встанет на место само:
запрошенная колонка попадёт в явную сетку, а `-1` снова окажется последним.

## `max-width` на гриде даёт горизонтальный скролл

Лечится вложением: внешний грид тянется на `100%`, внутренний ограничен.

```css
.outer { display: grid; }                       /* тянется по родителю */
.inner { max-width: 900px; display: grid; }     /* ограничен, скролла нет */
```

# Ступенчатые колонки без медиазапросов

Поправка к `css-layout.md`: последовательность **4 → 2 → 1 без промежуточной тройки
достижима и без медиазапросов**. Два способа.

## Способ 1: вложенные гриды (внешний квантует ширину)

Идея: внешний грид считает треки **по максимуму** (значение определённое), поэтому он
переключается скачком — 2 колонки или 1. Внутренний считает **по минимуму** (`1fr`),
поэтому заполняет выданную ширину: 4, 2 или 1.

```css
:root { --cell: 250px; }

.outer {
  display: grid;
  max-width: calc(var(--cell) * 4);
  grid-template-columns: repeat(auto-fit, minmax(calc(var(--cell) * 0.9), calc(var(--cell) * 2)));
}

.inner {
  grid-column: 1 / -1;
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(calc(var(--cell) * 0.83), 1fr));
}
```

```
ширина ≥ 1000px   → внешний 2 трека → внутренний 4 колонки
ширина ≥  500px   → внешний 1 трек  → внутренний 2 колонки
ширина <  500px   → внешний 1 трек сжимается → внутренний 1 колонка
```

Позиции детям задавать не нужно — внутренний грид сам переносит их.

## Способ 2: `clamp` как переключатель

Приём известен как «Fab Four»: выражение `(620px - 100%) * 1000` даёт либо огромное
положительное, либо огромное отрицательное число, и `clamp` схлопывает его в одну
из границ. Получается булев переключатель на чистом CSS.

```css
.m {
  display: grid;
  justify-content: start;
  grid-template-columns: repeat(auto-fill,
    clamp(clamp(100px, (620px - 100%) * 1000, 30%), (320px - 100vw) * 1000, 100%));
}
```

Для резиновых колонок то же самое заворачивается в `minmax(…, 1fr)`:

```css
grid-template-columns: repeat(auto-fit, minmax(
  clamp(clamp(100px, (620px - 100%) * 1000, 30%), (320px - 100vw) * 1000, 100%), 1fr));
```

Читается тяжело — но работает там, где медиазапрос не подходит, потому что мерит
**свой контейнер** (`100%`), а не окно. Сегодня для этого обычно проще взять `@container`.

## `subgrid` — выровнять вложенное по трекам родителя

```css
.grid {
  display: grid;
  gap: 1rem;
  grid-template-columns: [column-1] 20ch [column-2] 1fr;
  grid-auto-rows: min-content;
}
.grid > .subgrid {
  grid-column: 1 / -1;
  display: grid;
  grid-template-columns: subgrid;   /* берёт 20ch 1fr у родителя */
}
```

Без `subgrid` внутренняя сетка считает свои треки сама, и колонки соседних блоков
не совпадают.

# Инлайновый бокс: content area, line box, strut

Три разные высоты, которые постоянно путают:

| Что | Чем определяется | На что влияет |
|---|---|---|
| **Content area** | метрики шрифта (`font-size`, ascender/descender) | где рисуются `background`, `border`, `outline` |
| **Line box** | наибольшее из всего, что стоит на строке | реальная высота строки в потоке |
| **Strut** | `font-size` + `line-height` **родителя** | подпирает высоту строки, даже если весь контент мелкий |

Отсюда следствия, которые выглядят как баги:

- **`padding` у `display: inline` не увеличивает высоту строки.** Он увеличивает площадь
  фона и может налезть на соседние строки, но line box не растёт. Лечится только
  `display: inline-block` или `line-height`.
- **Строка выше, чем ожидалось, хотя текст мелкий.** Виноват strut: он берёт метрики
  родителя. Уменьшать надо `line-height`/`font-size` у родителя, а не у `span`.
- **`font-size` больше `line-height`** — line box всё равно растянется под шрифт,
  `line-height` его не обрежет.

Поэтому в меню и ссылках высоту задают через `line-height`, а не вертикальным `padding`:
хитбокс `<a>` растёт честно, а строка не скачет при появлении иконок.

## Фон, не рвущийся между строк

```css
p    { font-size: 16px; line-height: 1.5; }
mark {
  background: #ffcc00;
  padding: 0.25em 0;              /* 1. добить фон до высоты строки */
  margin:  -0.25em 0;             /* 2. вернуть padding обратно, чтобы строки не разъехались */
  box-decoration-break: clone;    /* 3. фон повторяется на каждой строке переноса */
  -webkit-box-decoration-break: clone;
}
```

## Центрирование по виртуальной baseline

Проблема: `vertical-align` внутри строки двигает **всю строку** — соседние элементы
уезжают. Решение — дать каждой ячейке собственную baseline, от которой и считать.

```html
<div style="display:flex">
  <div>Обычный текст в строке</div>

  <div class="middleClass" style="border:1px solid red; display:inline-block;">
    xOnBaseLine-x<span style="vertical-align:middle">центрировано по высоте капители</span>
  </div>
</div>
```

```css
.middleClass::before {
  content: 'g';                /* невидимый символ задаёт baseline */
  display: inline-block;
  vertical-align: middle;
  height: 100%;
  width: 0;
  overflow: hidden;
}
```

Числа условные, для наглядности — но порядок шагов и уравнения настоящие.

**1. Baseline рождается раньше `::before`, по причине X.** `.middleClass` — `inline-block`,
для своего контента сам заводит line box. Первое, что в него кладётся — ещё до единого
символа — невидимый **strut** со шрифтом/`line-height` **самого `.middleClass`**. У него
есть baseline, и она садится в конкретную точку страницы, скажем `Y = 100px`. Причина X:
чистая функция шрифта контейнера, посчитанная до контента.

**2. От неё, тоже без участия детей, считается точка-цель для `middle`.** Правило: центр
`middle`-бокса = `baseline + x-height/2`. Пусть `x/2 = 4px`. Точка-цель `A = 104px` —
тоже прибита шрифтом `.middleClass`, `::before` ещё не появился.

**3. `::before` приходит со своей безусловной геометрией.** У любого бокса центр — на
`H/2` от его же верха. Это факт про прямоугольник, не CSS-правило. Пусть `H = 60px` —
центр обязан быть в 30px от собственного верха `::before`.

**4. Одно уравнение, один неизвестный.** Правило `middle` требует: центр `::before` = `A`.
Геометрия требует: центр = верх + `H/2`. Значит верх `::before` = `A − H/2 = 74px`,
низ = `134px`. Тут никто не уступает — это подстановка, а не переговоры: `.middleClass`
ничего не отдавал, `::before` просто встал в единственную точку, где верны оба факта.

**5. А вот здесь — то, что твоя метафора ловит верно.** Line box — отдельная, третья
сущность: оболочка вокруг уже расставленных. У strut'а верх был на `85px` (`Y − ascent`).
У `::before` верх — `74px`, выше. Значит верх строки **уезжает** с `85` на `74`.
Расстояние «от верха строки до baseline» было `100 − 85 = 15px`, стало `100 − 74 = 26px`.
Это число реально выросло — но не потому, что `A` или `Y` сдвинулись (они как были `104`
и `100`, так и остались), а потому, что сдвинулся верх оболочки, которую сам `::before`
и раздвинул.

**6. Почему `<span>` попадает в центр.** Он считает то же уравнение шага 4 относительно
той же, ни разу не тронутой `A = 104`. Строка, раз `::before` встал симметрично вокруг
`A` (30px вверх, 30px вниз), сама вышла симметричной: `[74, 134]`, середина — `104`.
`A` и есть центр итоговой оболочки — не потому что кто-то подгонял, а потому что
единственный доминирующий участник (`::before`) сам был центрирован вокруг неё.
strut и `<span>`-текст в этом уравнении не участвуют — им до `A` от силы ascent шрифта,
пара пикселей, — поэтому именно `::before` **в одиночку** решает форму строки.

Итого: двигается в буквальном смысле верх строки (оболочка) и, как следствие, расстояние
от него до baseline. Точка `A`, куда целятся все `middle`, как была прибита шрифтом
`.middleClass`, так и осталась.

Тот же приём короче, если контейнер можно сделать flex-ом: `align-items: center`.
Трюк с `::before` нужен там, где элементы обязаны остаться инлайновыми — вперемешку
с текстом.

# Переносы текста

Пять свойств держат в голове тяжело, потому что они не варианты одного и того же —
это три РАЗНЫХ вопроса, просто заданных вперемешку. Разложить по вопросам:

```
Перенос текста
│
├─ ПЕРЕНОСИТЬ ЛИ СТРОКУ ВООБЩЕ
│  └─ white-space: normal | nowrap | pre | pre-wrap | pre-line
│      это шорткат ИЗ ДВУХ независимых осей (таблица ниже):
│      white-space-collapse  — схлопывать пробелы/переносы источника или нет
│      + text-wrap-mode      — wrap | nowrap, тот же переключатель, что и ниже
│
├─ ГДЕ ВНУТРИ СЛОВА можно разорвать — два свойства выглядят близнецами, но по-разному
│  │  СРАБАТЫВАЮТ: у одного точки разрыва наравне с пробелом, у другого — только когда
│  │  вариант "перенести слово целиком" уже испробован и не сработал.
│  │
│  ├─ word-break: normal | break-all | keep-all
│  │   инструмент "рубить, не пытаясь сперва перенести". Его точки разрыва —
│  │   РАВНОПРАВНЫЕ С ПРОБЕЛОМ, участвуют в обычной раскладке строки всегда,
│  │   даже если слово целиком прекрасно поместилось бы на следующей строке —
│  │   браузер может разорвать его посреди, просто чтобы плотнее набить текущую.
│  │   break-all: даёт ЛАТИНИЦЕ то, что иероглифы (китайский/японский) и так имеют
│  │     по умолчанию — разрыв между любыми двумя символами.
│  │   keep-all: наоборот, ОТКЛЮЧАЕТ это дефолтное поведение у иероглифов и хангыля
│  │     (корейский), заставляя их переноситься по словам/пробелам, как латиницу.
│  │
│  ├─ overflow-wrap: normal | break-word | anywhere
│  │   инструмент "сначала перенести слово целиком, и только если оно и на пустой
│  │   строке одно не помещается — тогда делить". Это ПОСЛЕДНИЙ ШАНС: браузер уже
│  │   попробовал обычный перенос всего слова на новую строку; включается, только
│  │   если слово шире самой строки. Новых точек, конкурирующих с пробелом, не создаёт.
│  │   break-word: рвёт, но НЕ уменьшает min-content (спец. исключение спеки)
│  │   anywhere:   рвёт, и min-content схлопывается до 1 символа
│  │
│  └─ line-break: auto | loose | normal | strict | anywhere
│      loose/normal/strict — правила пунктуации у иероглифов (китайский/японский);
│      на латинице визуально не заметны
│      anywhere — как overflow-wrap:anywhere, плюс игнорирует пунктуацию вообще
│
└─ КАК КРАСИВО разложить уже РАЗРЕШЁННЫЕ переносы по строкам
   └─ text-wrap: wrap | nowrap | balance | pretty | stable
       ничего не запрещает и не разрешает — выбирает из уже валидных точек, чтобы
       строки вышли ровнее (balance) или без "сирот" (pretty)
```

Итого порядок мысли: сначала `white-space`/`text-wrap-mode` решают, переносить ли
строку вообще; `word-break` работает наравне с пробелом ВСЕГДА (даже без переполнения),
`overflow-wrap` — только когда перенос слова целиком уже не спас; `line-break`
добавляет к этому иероглифическую пунктуацию; и только в конце `text-wrap: balance/pretty`
выбирает красивую раскладку среди уже разрешённого.

## Главное: что происходит с `min-content`

Это то, из-за чего ломается вёрстка во flex и grid:

| Значение | `min-content` элемента | Итог |
|---|---|---|
| по умолчанию | самое длинное слово | колонка не может стать уже длинного слова |
| `overflow-wrap: break-word` | **самое длинное слово** (не меняется!) | рвёт слово только при реальном переполнении |
| `overflow-wrap: anywhere` | **1–2 символа** | колонка может схлопнуться в букву |
| `word-break: break-all` | 1–2 символа | то же, но рвёт всегда, не только при переполнении |

Практика: `anywhere` **обязательно** сопровождать `min-width`, иначе во flex/grid колонка
сожмётся до одного символа. `break-word` в этом смысле безопаснее.

И общее: браузер считает ширину как `max(min-width, min(width, max-width))`. Если ничего
не задано и родитель не ограничивает — переноса не будет вовсе.

## `white-space`

| Значение | Пробелы | Переводы строк | Перенос по ширине |
|---|---|---|---|
| `normal` | схлопывает | игнорирует | да |
| `nowrap` | схлопывает | игнорирует | **нет** |
| `pre` | сохраняет | сохраняет | нет |
| `pre-wrap` | **сохраняет** | сохраняет | да |
| `pre-line` | схлопывает | **сохраняет** | да |

Убрать пробел, появившийся из-за переноса строки в разметке, можно комментарием:

```html
<div><!--
  -->Название: <span>значение</span>
</div>
```

## Устаревшее

`word-break: break-word` — нестандартное значение, эквивалент `overflow-wrap: anywhere`
(+ `word-break: normal`). Писать вместо него сразу `overflow-wrap: anywhere`.

# Измерения элемента

| API | Content | Padding | Border | Scrollbar | Учитывает `transform` |
|---|---|---|---|---|---|
| `clientWidth/Height` | ✅ | ✅ | ❌ | ❌ | ❌ |
| `offsetWidth/Height` | ✅ | ✅ | ✅ | ✅ | ❌ |
| `getBoundingClientRect()` | ✅ | ✅ | ✅ | ✅ | ✅ |

- `offsetWidth` — место, занимаемое элементом в родителе; **border входит всегда**.
- `box-sizing: border-box` меняет только то, как трактуются заданные `width`/`height`.
  На расчёт `offsetWidth`/`clientWidth` он не влияет.
- `transform` не меняет поток, поэтому не меняет ни одну layout-метрику. Он виден только
  в `getBoundingClientRect()`, который отдаёт визуальные габариты относительно вьюпорта.
- `offsetLeft`/`offsetTop` считаются не от прямого родителя, а от **`offsetParent`** —
  ближайшего предка с `position` ≠ `static` (или `<body>`, если такого нет). Это **не**
  containing block (ниже): для `static`-элемента containing block — почти всегда прямой
  родитель, а `offsetParent` может оказаться на несколько уровней выше. Отсюда баг:
  `offsetLeft` внезапно меряет расстояние не от соседа, а от далёкого позиционированного
  предка.

## ResizeObserver: `borderBoxSize` vs `contentRect`

```
borderBoxSize   внешний бокс. Появился скроллбар — значение НЕ изменилось.
contentRect     место под контент. Появился скроллбар — ширина уменьшилась.
```

Для «поместится ли контент» нужен `contentRect`. Для «какой размер у элемента
в layout» — `borderBoxSize`.

# Проценты и containing block

**`margin-top: 10%` и `padding-top: 10%` считаются от ШИРИНЫ containing block, не от
высоты.** Это не баг, так в спецификации — и именно на этом построен старый трюк
с пропорциональными блоками (сегодня его заменяет `aspect-ratio`).

Containing block определяется так:

| Позиционирование элемента | Containing block |
|---|---|
| `static` / `relative` | content box ближайшего блочного предка |
| `absolute` | **padding box** ближайшего позиционированного предка |
| `fixed` | вьюпорт |
| внутри `transform`/`filter`/`will-change` предка | этот предок, даже для `fixed` |

Ловушка с вложенными `absolute`:

```
div            → обычный
  └ absolute   → выпал из потока, размер 0×0 (содержимое его не растит)
      └ absolute (проценты) → считает от 0×0, то есть от нуля
```

Абсолютный элемент не влияет на размер родителя, поэтому промежуточный absolute-контейнер
без явных размеров схлопывается, и все проценты внутри превращаются в ноль.
